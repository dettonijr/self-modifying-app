# Decisions

A running log of details and smaller decisions that matter later: constraints found while building, conventions, known limitations. Larger trade-offs live in `docs/adr/`; vocabulary lives in `GLOSSARY.md`; the plan lives in `.scratch/self-modifying-app/spec.md`.

Newest entries at the bottom. Each entry notes where it came from.

## Runtime and tooling

- **TypeScript runs directly on Node, with no build step** (ticket 01). Node ≥ 22.18 strips types natively, so imports must use `.ts` extensions and only erasable TS syntax is allowed: no `enum`, no `namespace`, no parameter properties.
- **npm, not pnpm** (ticket 01). pnpm isn't installed in the dev environment.
- **The Docker image is `mcr.microsoft.com/playwright:v1.64.1-noble`** (ticket 07, replacing `node:22` from ticket 01). It ships Node 24, git, and Chromium with its system libraries. Installing those libraries on `node:22` fails because `deb.debian.org:80` needs host approval in the sandbox. `playwright` is a runtime dependency pinned to exactly `1.64.1`; it must match the image tag whenever either is upgraded.
- **The dev machine has Chromium's system libraries and Playwright's Chromium installed** (ticket 01). Recorded in `/home/agent/.t3/notes/self-modifying-app/env.md`.
- **The dev machine's Node can't run `.ts` files** (ticket 12). Debian's Node build has `process.features.typescript === false` (`ERR_NO_TYPESCRIPT`), so `npm start` and `node src/*.ts` fail here; they work in the `node:22` Docker image, or locally with the official Node build or `nvm`. Tests must call code in-process instead of spawning `node src/*.ts`.

## Platform structure

- **The Agent interface is `run(task)`, returning a stream of `progress` and `usage` events that ends in exactly one `result`** (ticket 01). The running platform uses `unavailableAgent` until ticket 03 adds the real Claude Agent. Tests use `FakeAgent`, with a `Gate` that holds a Run until the test releases it.
- **The test harness is `startTestPlatform()`** (ticket 01). Each test gets a fresh platform on random ports with a temporary data folder. See the README.
- **Run lifecycle lives in `runs.ts`, Landing in `lander.ts`** (ticket 02). `Runs` validates Prompts (500 characters, `MODELS`, nickname from the `nickname` cookie) and drives each Run: worktree at `<data>/worktrees/<runId>` on branch `run/<runId>`, the Agent, the Lander, then removal of the worktree. A Run's final state (`landed`/`rejected`) is published only after its worktree is removed, so a Player who sees it finish can send the next Prompt. Prompts sent while a Run is in progress get 409 for now (ticket 05 replaces this with the queue).
- **Landing moves `main` with `git update-ref` and the expected old value** (ticket 02), so it's a compare-and-swap that fails if `main` moved. It never touches the Canvas repo's working folder, which goes stale after the first Land. Nothing should read or commit through that folder. Ticket 06 must rebase onto the latest `main` before the swap.
- **Commit metadata is git trailers** (ticket 02). The message is `<Kind> by <nickname>: <summary>`, a blank line, the Prompt verbatim, a blank line, then `Kind:`, `Nickname:` and `Model:` trailers. `CanvasRepository.history()` reads only commits with a `Kind` trailer. Replay and Rollback should add their reference to the original commit as another trailer.
- **A Run whose Agent changes nothing is rejected** (ticket 02), with nothing committed.
- **Console API so far** (ticket 02): `POST /api/prompts` `{prompt, model?}` with the nickname cookie returns 202 and the Run, or 400 or 409. `GET /api/runs/:id` and `GET /api/history` (newest first: commit, kind, nickname, prompt, model, time). The Console UI polls these until ticket 05 adds the WebSocket.

## The real Claude Agent

- **`ClaudeAgent` is used when `ANTHROPIC_API_KEY` is set, otherwise `unavailableAgent`** (ticket 03, `agentFromEnvironment`). The key goes only into the environment of Claude's own process and is masked in error messages.
- **Per-Run caps: `RUN_TIME_LIMIT_SECONDS` (default 600) and `RUN_TOKEN_LIMIT` (default 2,000,000)** (ticket 03). Invalid values stop the platform at startup. The token cap is checked after each message, so a Run can go slightly over before it stops. Going over a cap fails the Run with a message naming the cap.
- **How Claude is confined** (ticket 03): only the `Read`, `Write`, `Edit`, `Glob` and `Grep` tools. The shell, web, subagents and notebooks are also refused by name. A permission check allows only absolute paths inside the worktree, resolves symlinks first, and refuses anything under `.git`.
- **The Agent never loads settings, hooks or MCP servers from disk** (ticket 03). A Prompt can write `.claude/settings.json` or `.mcp.json` into the Canvas, which could otherwise run commands. Never switch this on. Because of it, the Agent reads the worktree's `CLAUDE.md` itself and adds it to the system prompt along with the platform's rules.
- **Token usage counts cached input as input** (ticket 03), so costs come out slightly high. Usage events are deltas; the final event tops up the difference to the SDK's totals, so the sum of usage events is authoritative.
- **Progress events cover only `Write` and `Edit`** (ticket 03), each saying "Editing <path relative to the worktree>".
- **Dependency: `@anthropic-ai/claude-agent-sdk` 0.3.316** (ticket 03). It ships the Claude executable as a separate package per platform, which `npm ci` in Docker installs to match the image.
- **Smoke test: `CLAUDE_SMOKE_TEST=1` plus `ANTHROPIC_API_KEY`** (ticket 03). It uses Sonnet 5.5 and passes when the page's `<h1>` or `<title>` becomes "Hello". Verified 2026-10-31: inside the Docker container, with only the dummy key, no Claude credential files and traffic routed through the sandbox proxy (local `docker-compose.override.yml`), real Prompts Landed. So the sandbox proxy does replace the key on requests to the Anthropic API, even though the sandbox reports `SBX_CRED_ANTHROPIC_MODE=none`. Which credential it uses (API key or the host's Claude login) is configured on the host and isn't visible from inside the sandbox. Outside the sandbox a real `ANTHROPIC_API_KEY` is needed.

## Canvas serving and live reload

- **Canvas pages are served at `/@<commit>/<path>`** (ticket 04). A live URL redirects (302) to the same page at `main`'s commit, so relative URLs resolve inside that commit. Commit-pinned non-HTML files are cached as immutable; HTML and live URLs are `no-cache`. Only full 40-hex commits are accepted. Absolute URLs aren't pinned, so the Canvas `CLAUDE.md` tells Claude to use relative URLs. Chosen over `<base href>`, which breaks `#anchor` links; the commit shows in the address bar.
- **The live Canvas serves a pinned commit only if it's on `main` (`repo.isOnMain`); others get 404** (code review, replacing ticket 04's "any commit"). Commits found on `main` are cached for the server's lifetime, which relies on `main` only moving forward. The render check's private server passes `anyCommit: true` to serve the candidate.
- **`/__platform/` belongs to the platform and Canvas files there are never served** (ticket 04). It holds `platform.js` and `events`; ticket 11's client library and endpoints go under it too.
- **The platform script is injected into every `.html` file** (ticket 04): right after `<head …>`, otherwise after the doctype, otherwise at the start. Its UI sits in an open shadow root (`<platform-overlay>`), so Canvas CSS can't touch it.
- **The Canvas real-time channel is Server-Sent Events at `GET /__platform/events`** (ticket 04). Platform events use the SSE event name `platform`: `hello {commit, running}` first on each connection (late viewers get banners; an old page reloads), then `run-started`, `landed` and `rejected`. Ticket 11 should use its own event name and send viewer→server messages by POST under `/__platform/`, guarded by `isCrossOrigin()`.
- **Known limit: each open Canvas tab holds one HTTP/1.1 connection, and browsers allow about 6 per origin** (ticket 04). Many Canvas tabs in one browser could starve each other; moving to WebSocket would fix it.
- **`Runs.onChange(listener)` and `Runs.inProgressRuns()`** (ticket 04) drive Canvas events. `onChange` fires on running, landing, then landed/rejected (after the worktree is removed). Ticket 05's Console WebSocket can use the same hook.
- **The reload notice survives the reload through `sessionStorage`** and shows for 6 seconds (ticket 04).
- **Known limitation: if a Land deletes the page a viewer is on, the reload ends at a 404** (ticket 04).

- **"View the Canvas at this version" opens a pinned, read-only view at `/@<commit>/?version`** (user, 2026-10-31; log ticket 02). Found bug it fixes: the injected script's catch-up (`hello` with a different commit) and reload-on-Land bounced old versions straight back to live. A separate origin for old versions was rejected as overkill.
- **With the `version` marker, the platform script ignores all `platform` events** (no catch-up, no reload on Land, no "changing"/"changed by" banners) but still opens the EventSource, so `__platformEvents` and feature messages work. It shows `p.version`, "Older version: view only · Go to the live Canvas", in the shadow overlay; the link goes to the live entry page `/` (log ticket 02). Because the current platform script is injected at serve time, this works on versions older than the feature, and old CSS can't hide it (`:host !important` rules win; tested with `display:none !important`).
- **Same-origin links under `/@<commit>/` get `version` added by a capture-phase click listener** (log ticket 02). Script navigation or links opened without a click lose it; the server rule still makes those pages read-only, and the library drops the refused writes quietly.
- **Read-only, two layers** (log ticket 02): `canvas-services.js` decides view-only from its own `location` and makes `set`/`delete`/`send` no-ops (bad keys and `set(key, undefined)` still throw; reads and `onMessage` unchanged). On the server, `handleServiceRequest` takes optional `isViewOnly(req)` and refuses non-`GET`/`HEAD` with 403 "Older Canvas versions are view only" plus a `console.warn`. The Canvas server's rule: the `Referer` path is `/@<commit>/` and either has `version` or its commit isn't `repo.main()`; no `Referer` or a live URL is allowed. The render check's server gets no `isViewOnly` (a test guards that a candidate that writes still renders).
- **A normal tab briefly on a non-`main` commit (between a Land and its reload, or before catch-up) has its writes refused with 403 plus `x-platform-view-only: 1`, and the library drops them quietly like a pinned view's** (log ticket 02; user decision in log review). Only 403s carrying that header are dropped; other 403s (e.g. cross-origin) still throw.
- **Banner look: `--color-text` on `--color-surface`, 5px `--color-warning` left border, link in `--color-accent`, all AA; the link is at least 44px; `pointer-events: auto`** (log ticket 02).
- **The pinned-view definitions live once in `src/canvas-versions.ts`: `PINNED_PATH`, `VERSION_MARKER`, `VIEW_ONLY_HEADER`, `pinnedViewPath()`** (log review). The two browser scripts read them from a `__PLATFORM_VERSIONS__` placeholder the Canvas server fills in; `withVersionDefinitions` throws at startup if it's missing, so the raw `.js` files only work when served. `/api/canvas` returns `{port, versionPath}` with a `{commit}` placeholder, which the Run page uses for the link.
- **Test technique: the stale-tab test keeps a normal tab on an older commit by blocking `/__platform/events` in Playwright**, so `hello` never triggers the catch-up reload (log review).
- **Accepted limit: code that strips `Referer` could still write** (log ticket 02).
- **Test pitfall: when one test writes and deletes the same key over HTTP, send the requests sequentially** (log ticket 02).
## Landing

- **The Lander lands one Run at a time, in the order Runs reach `land()`, using a chain of promises** (ticket 06). Each Land: commit the worktree, read the current `main`, rebase with `CanvasRepository.rebaseWorktree(worktree, onto)`, run the render check, then move `main` with the compare-and-swap, expecting the `main` it rebased onto.
- **`LandFailure` is `"unchanged" | "conflict" | "render"`** (ticket 06). A conflicting rebase is aborted and returns `conflict`, with the message "The change conflicts with one that Landed while it was being made". Ticket 08 builds its handling on this.
- **Test pitfall: `FakeAgent` hands out scripts in the order Runs start, and worktree creation can reorder them under load** (ticket 06). Tests that hold a specific Run must wait with `agent.started(n)` before sending the next Prompt, or pick behaviour from `run.task.instructions`.
- **Tests that assume one Run at a time set `maxParallelRuns: 1`** (ticket 06), e.g. `queue.test.ts` and `console-ui.test.ts`.

## Conflict handling

- **A Land that fails with `conflict` or `render` goes `resolving → landing` up to `MAX_RESOLUTION_ATTEMPTS` (2), then `restarted → landing` once in a fresh worktree on the latest `main`, then `rejected`** (ticket 08). `unchanged` and Agent failures are rejected straight away. The restart gets no resolution attempts of its own.
- **Rejection message after a failed restart** (ticket 08): `COLLIDED_MESSAGE` for a conflict, "Canvas didn't render" for a render failure, or the Agent's own error.
- **The flow lives in `runs.ts` (`workAndLand` → `inWorktree` / `workOnce` / `workAndResolve` / `resolve`); constants, `resolutionInstructions()` and `hasConflictMarkers()` are in `src/resolution.ts`** (ticket 08). A Run's instructions and commit metadata are set in `workOnce` / `change()`, so Rollback and Replay get resolve → restart → reject for free by giving their Runs their own instructions and metadata.
- **Resolution always uses `RESOLUTION_MODEL` (Sonnet 5.5), and its usage counts toward the Run under that model** (ticket 08; tokens-and-cost).
- **Repository methods** (ticket 08): `reopenOnto(worktree, change, onto)` resets to `onto` and reapplies the change with `cherry-pick --no-commit`, returning conflicted paths with markers kept; `head(worktree)`; `changesBetween(from, to, paths?)`, oldest first, sharing parsing with `history()`. `Worktree.base` records the commit a worktree was created from.
- **What the resolving Agent is told** (ticket 08): for a conflict, the conflicted files, the Run's Prompt, and the nickname and Prompt of each commit since the base that touched those files; for a render failure, the problem (`LandResult.problem`) and every commit since the base.
- **Each Land is still exactly one commit** (ticket 08): a resolution leaves the change uncommitted on top of `main`. If reapplying onto the latest `main` is clean, the Agent isn't called. A failed attempt (Agent fails, conflict markers remain, or the next Land fails) starts the next one from the last committed change.
- **No resolution or restart starts once a Run's abort signal fires** (ticket 08), which fits restart resume.
- **Known limitation: a Run resumed after a platform restart gets a fresh set of resolution attempts and restart** (ticket 08).
- **The Console shows `resolving` and `restarted` like `running`, with a yellow badge** (ticket 08).
- **Test pitfall: resolution requests use up `FakeAgent` scripts too** (ticket 08). Tell them apart by `task.instructions !== prompt`. A test expecting rejection must queue scripts for both resolutions and the restart, or the extra attempts fail with "no script queued" and the reason changes.
- **Known flake: under full-suite load, one Playwright test in `platform-services.test.ts` once hit its 30s timeout** (ticket 08); it passed on rerun.

## Replay

- **`POST /api/replays` with `{commit, model?}` and the nickname cookie** (ticket 10) answers 202 with the Run, or 400 (no nickname or bad model), 404 (commit isn't a change on `main`, including the starter Canvas; reason `not-found`), or 409 (`already-waiting`). Harness: `platform.replay({nickname, commit, model?})`.
- **Change kinds are listed in `CHANGE_KINDS` in `canvas-repository.ts`, and each kind's behaviour is in `CHANGE_KIND_RULES` in `src/change-kinds.ts`** (ticket 10; code review): `playerPicksModel`, an optional `mechanically` step with its "nothing to do" message, `instructions(repo, worktree, run)` and `intent(run)`. A new kind needs an entry in both. `history()` and `changesBetween()` list only listed kinds.
- **The reference to the original is two trailers, `Original: <sha>` and `Original-Nickname: <nick>`**, read back as `LandedChange.original = {commit, nickname}` (ticket 10). The nickname is stored so the credit needs no lookup. Rollback reuses the same field.
- **`RunView` has optional `kind` (absent means Prompt) and `original`, both saved by `RunStore`** (ticket 10). For a Replay, `run.prompt` is the original Prompt and `run.nickname` is the Player who replayed it.
- **Replay instructions are built each time work starts** (ticket 10, `CHANGE_KIND_RULES.Replay.instructions` → `replayInstructions()` in `src/replay.ts`). Later Prompts come from `changesBetween(original, worktree.base)`, so a Replay that waited or restarted gets the current list. The diff is cut at 40,000 characters (`MAX_DIFF_LENGTH`). Conflict resolution uses `run.prompt`, the original Prompt.
- **Repository methods** (ticket 10): `landedChange(commit)` returns a change only for a full 40-character hash on `main`; `diff(commit)` returns `git show` output.
- **`Runs.replay()` goes through the same `enqueue()` as Prompts** (ticket 10), so it uses the Player's one waiting slot.
- **Console: each history entry has "Fix it to this!", which opens an inline confirmation with a "Replay model" dropdown** that survives history refreshes (ticket 10). History shows "↻ Alice replayed Bob's 'prompt' `abc1234`"; Replay Runs are marked ↻ in the Runs and queue lists.

## Rollback

- **`POST /api/rollbacks` with `{commit}` and the nickname cookie** (ticket 09) answers 202 with the Run, or 400 (no nickname), 404 (`not-found`), 409 (`already-waiting`). `Runs.rollback()` uses the same `enqueue()` as Prompts and Replays.
- **A Rollback Run has `kind: "Rollback"`, `original: {commit, nickname}`, the original change's Prompt as `prompt`, the rolling-back Player as `nickname`, and always `DEFAULT_MODEL` (Sonnet 5.5)** (ticket 09). Players can't pick a model for a Rollback.
- **Rollback commits use the same `Original:` / `Original-Nickname:` trailers as Replay, with the subject `Rollback by <nick>: <original prompt>`** (ticket 09).
- **A Rollback first tries `CanvasRepository.revert(worktree, commit)` (`git revert --no-commit`); if that's clean the Agent isn't called** (ticket 09). If it conflicts, the worktree is reset and the Agent gets `rollbackInstructions()` from `src/rollback.ts` (original Prompt and author, the diff cut at `MAX_DIFF_LENGTH`, and later Prompts), starting from the latest Canvas with no conflict markers. The restart repeats revert-then-Agent.
- **Conflict resolution is told the Run's intent from `CHANGE_KIND_RULES[kind].intent`** (ticket 09; code review): for a Rollback that's `rollbackIntent()` ("Roll back X's change … keeping everything after"), so the resolver doesn't re-apply the change. Prompts and Replays still use `run.prompt`.
- **Rolling back a change that's already undone is rejected with `ALREADY_ROLLED_BACK_MESSAGE` ("That change is already undone")** (code review), used when the mechanical revert applied cleanly and the Lander reports `unchanged`.
- **"Roll back" sits next to "Replay", each with an inline confirmation; only one confirmation is open per entry** (ticket 09; Prompts list). A Rollback reads "↩ Alice rolled back Bob's 'prompt' `abc1234`".

## Render check

- **The render check is its own step in the Lander** (ticket 07): commit the worktree, run the check, then move `main`. Failures return `failure: "render"` (reason "Canvas didn't render") or `failure: "unchanged"`; ticket 08 routes on `failure`. The specific problem is only logged with `console.warn`; Players see "Canvas didn't render".
- **The check uses a private Canvas server on a random loopback port with its own channel** (ticket 07), so it never appears as a viewer of the live Canvas. It loads `/@<commit>/`. One Chromium starts on the first check and is reused until the platform closes. Page load times out after 10s, and the page is then checked as it stands.
- **Doesn't render means any of:** the entry page returns an error status (e.g. `index.html` deleted); the entry page's own inline scripts throw an uncaught error; or the body is blank, with no text and no visible sized element (the platform overlay sits outside `<body>` and doesn't count) (ticket 07).
- **Errors in a feature's own files and unhandled promise rejections don't count** (ticket 07), so a broken feature that still renders Lands, as designed.
- **Test fixtures must leave something visible in `index.html` to Land** (ticket 07); bare text like `"x"` is enough.

- **The render check loads each candidate twice in the one shared Chromium, each in a fresh context: desktop (1280×720), then phone (390×844, `isMobile`, `hasTouch`, `deviceScaleFactor: 3`)** (Prompts list ticket 07). It stops at the first failure; both loads share the private server and in-memory store. The same blank/crash rules apply at both sizes; layout and sideways scrolling aren't checked. Each check now takes about twice as long.
- **`LandResult.problem` starts with the screen, e.g. "On a phone-sized screen (390×844, touch): The page is blank"** (ticket 07), so the conflict-fixing Agent knows it failed on a phone. Players still see "Canvas didn't render".
- **A `<body>` that isn't drawn at all (`display: none`) counts as blank** (ticket 07, fixing a desktop bug too).
- **With `isMobile`, a page without a viewport meta is laid out about 980px wide**, so phone-only CSS only applies when the tag is present (ticket 07). Test fixtures targeting phone layouts need it.
## Queue and the Console WebSocket

- **The parallel Run limit starts from `MAX_PARALLEL_RUNS` (default 3) and can be changed during play with `npm run set-parallel-runs -- <n>`** (tickets 05, 06; code review). The command writes `<data>/parallel-runs.json` as `{maxParallelRuns}`; once that file exists it wins over the environment variable, including after a restart. The value can go up or down; lowering never stops Runs in progress. Code is in `src/parallel-limit.ts`; `Runs` takes `maxParallelRuns` as a number or a function, and the platform passes one that re-reads the file.
- **One waiting Prompt per Player is an exact match on the trimmed nickname** (ticket 05). A second one gets 409 with reason `already-waiting`. The slot frees as soon as the Prompt starts running.
- **The Console WebSocket is `/api/live`, using the `ws` package** (ticket 05). On connecting, a client gets `{type:"snapshot", queue, runs}`, then `queue`, `run` (every state change) and `progress` messages. The snapshot holds Runs in progress plus the last 20 finished; each Run view keeps its latest 50 progress events. Types are `RunsEvent` and `RunsSnapshot` in `runs.ts`.
- **`Runs.subscribe(listener)` gets every Run event** (ticket 05). Ticket 04's `onChange` wraps it, so it also fires for `waiting`, which the Canvas channel ignores.
- **WebSocket upgrades go through `isCrossOrigin()` (403) and get 404 for any other path** (ticket 05). Any future WebSocket must do the same.
- **Closing an HTTP server doesn't close upgraded sockets** (ticket 05). The Console server terminates its WebSocket clients when it closes; any new WebSocket server must too, or `platform.close()` hangs.
- **The Console page gets Run status from the WebSocket and reconnects 1 second after it closes** (ticket 05). History refreshes on connect and on each Land.
- **`playwright` is a runtime dependency, `ws` a dependency, `@types/ws` a dev dependency** (merge of 05 and 07).
- **Harness: `platform.live()` returns a WebSocket client with `messages` and `waitFor(match)`** (ticket 05).

## Platform services

- **Canvas code imports `{ channel, store }` from `/__platform/services.js`** (ticket 11; source `src/canvas-services.js`, which Claude can't edit). `channel(feature)` has `.send(msg)` and `.onMessage(fn)` (returns an unsubscribe function). `store(feature)` has `.get(key)` (`undefined` if missing), `.set(key, value)`, `.delete(key)` and `.list(prefix)` (returns `[{key, value}]` sorted by key). Values are any JSON. The feature name is the feature's folder name and must match `^[a-z0-9][a-z0-9_-]{0,63}$`.
- **Server API under `/__platform/`** (ticket 11, `src/platform-services.ts`): `POST channel/<feature>` with `{message}`; `GET|PUT|DELETE store/<feature>/<url-encoded key>` (`PUT` takes `{value}`, `GET` returns `{value}` or 404); `GET store/<feature>/?prefix=` returns `{entries}`. Every route refuses other origins with 403. Only `GET`/`HEAD` reach the rest of the Canvas server.
- **Limits: messages 16 KB, values 64 KB, keys 256 characters** (ticket 11).
- **Feature messages travel on the same SSE stream with event name `feature`**, data `{feature, message}` (ticket 11). They reach every viewer, the sender included, and aren't stored: a viewer only gets messages sent while their page is open.
- **One event connection per page** (ticket 11): the platform script exposes its EventSource as `window.__platformEvents` and the client library reuses it.
- **The key-value store uses Node's built-in `node:sqlite`, in `<data>/services.sqlite` (WAL mode), outside the Canvas repo** (ticket 11), so Land, Rollback and Replay never touch it. No new dependency; Node prints a one-time `ExperimentalWarning` at startup. Ticket 13 can reuse `node:sqlite` for the queue.
- **There are no atomic operations, so a concurrent `get` then `set` can lose an update** (ticket 11). The Canvas `CLAUDE.md` tells Claude to use one key per contribution plus `list()` for tallies. An `increment` operation could be added later if needed.
- **Each render check gets its own channel and an empty in-memory store** (ticket 11), so a candidate page can't change real data. Features see no stored data during the check, which is fine because a feature's own errors don't fail it.
- **`readJson(req, maxBytes)` and `sendJson` live in `http.ts`** (ticket 11) for reuse by any server.

## Restarts

- **The queue and Run records are saved in `<data>/runs.sqlite`** (ticket 13, `RunStore` in `src/run-store.ts`, `node:sqlite` in WAL mode), separate from `services.sqlite`. One row per Run: `seq` (send order), `id`, `state` as plain text with no constraint, and the rest of the Run as JSON without progress. New states and fields need no schema change, but **a new finished state must be added to `FINISHED` in `run-store.ts`**; anything else counts as unfinished.
- **Every state change is saved by `Runs.setState`**, plus once when a Prompt is queued (ticket 13). Always change state through `setState`.
- **`Runs.resume()` runs at startup, before the servers listen** (ticket 13): remove all leftover worktrees and `run/*` branches; reload the 20 most recently finished Runs; restart unfinished Runs from scratch on the latest `main` with the same id and Prompt; re-queue waiting Prompts in order.
- **Resumed Runs wait in a private `resuming` list that starts ahead of the queue, respecting the parallel limit** (code review, replacing ticket 13's "skip the limit"). They don't appear in the queue snapshot or take the Player's waiting slot, and their saved state is unchanged until they start. Their tokens are spent again, and earlier progress events are lost.
- **Agents must fail when aborted, never return success** (ticket 13). `close()` aborts Runs; one that doesn't Land stays saved as in progress and restarts on the next start.
- **Every Landed commit has a `Run: <id>` trailer, and `resume()` marks an unfinished Run as landed if its id is already on `main`** (code review), so a crash between moving `main` and saving `landed` can't Land a Prompt twice. `history()` is read only if some unfinished Run isn't waiting. `/api/history` entries include `run`.
- **`Runs` needs a `store: RunStore` in its constructor** (ticket 13).

## Spending cap (removed) and pricing

- **The game-wide spending cap was removed completely** (tokens-and-cost ticket 01, user decision 2026-10-31): no `Budget` class, game total, `spending.json`/`spending-cap.json`, `SPENDING_CAP_USD`, `spendingCapUsd` option, `raise-cap` command, `/api/spending` (404), `paused` refusal (no 503), paused banner, or pause-disabled buttons. The per-Run time and token limits are the safety net. `raise-cap` now prints the usage message (exit 2).
- **Prices live in `PRICES` in `src/pricing.ts`, per million tokens, for input, output, cache read and cache write** (tokens-and-cost tickets 01, 02). Sonnet 5.5: $2 / $10 / $0.20 / $2.50; Opus 5.5: $4 / $20 / $0.20 / $5.00. Source: the claude-api skill bundled with Claude Code (2.1.306, model table cached 2026-10-06) and its prompt-caching notes (5-minute cache writes cost 1.25× input). Opus 5.5's cache-read price really is $0.20 (0.05× input), stated explicitly in the reference, not the usual 0.1×. Not checked against Anthropic's live pricing page. **1-hour cache writes (2× input) aren't told apart**, so if Claude Code uses them the estimate runs low on writes.
- **Usage has four kinds: `TokenUsage` gains optional `cacheReadTokens` and `cacheWriteTokens` (absent = 0)** (ticket 02). `ClaudeAgent` reads `cache_read_input_tokens` / `cache_creation_input_tokens` (and the totals' `cacheReadInputTokens` / `cacheCreationInputTokens`); cached input is no longer counted as input. The per-Run token cap still counts all four.
- **Each Run saves `RunView.usageByModel` (four counts per model); new Runs start at `{}`** (ticket 02). Conflict fixes add under `RESOLUTION_MODEL`; start-overs and resumed Runs keep adding. A clean-revert Rollback shows zero.
- **`usage = {inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens, cost}` is computed on every read and never saved**, so a price change reprices old Runs (ticket 02). `RunSummary` carries `usage` but not `usageByModel`; `GET /api/runs/:id` returns both.
- **Every usage event saves the Run and sends a `run` message** (ticket 02), so busy Runs send many updates.
- **Runs without `usageByModel` (and Landed changes with no Run record) show "—" for good; their usage events are ignored, even after a start-over** (ticket 02; second review). New Runs start with `usageByModel: {}`.
- **Usage helpers live in `agent.ts`: `UsageCounts` (= `Required<TokenUsage>`), `USAGE_KINDS`, `zeroUsage()` and `addUsage(sum, usage)`** (second review), used by `claude-agent.ts` and `runs.ts`.
- **On startup the platform deletes obsolete data files listed in `OBSOLETE_DATA_FILES` in `platform.ts`** (currently `spending.json`, `spending-cap.json`; second review). Add future dead files there.
- **Display: "U (T) tokens · ~$C" via `tokenCount`, `usageLine`, `usageSpan` in `src/console-shared.js`, rendered as `span.usage` in `.details` after the time** (ticket 02). U = input + cache writes + output, T = U + cache reads. Under a cent it reads "<$0.01" (no "~"). Rounding promotes 999,960 to "1M", never "1000k". Formatting is tested through the rendered pages because TypeScript can't import the shared `.js` file.
- **Playwright pitfall: `hasText` matches across element boundaries and ignores case; select entries by `li[data-run="<id>"]`** (ticket 02).
- **Known flakes under full-suite load: `console-ui` "shows each Prompt once…" and `parallel-runs` "lets the host raise the limit…" timed out once at about 14s** (ticket 02); they passed on reruns.
- **The host runs Claude on their Claude Max subscription, not API billing** (user, 2026-10-31). Dollar figures are therefore estimates, not real spend; what actually limits play is Max's usage limits. When those are hit, Runs fail with a usage-limit error that the platform doesn't yet recognise (open question: pause on usage-limit errors?).

## Prompts list

- **`RunSummary = Omit<RunView, "progress">` in `runs.ts`** (Prompts list ticket 01): `id, state, nickname, prompt, model, kind?, original?, error?, commit?, time?`. `time` is when the Prompt was sent (or, for a Landed change with no Run record, when it Landed); older Landed Runs without one get the commit time at startup. Logs and files must stay out of the summary and be served only by `GET /api/runs/:id`.
- **`GET /api/runs` returns every summary, newest first, via `Runs.list()`**; `GET /api/runs/:id` returns the full view (ticket 01).
- **The live WebSocket's `snapshot` is `{queue, runs}`, with `runs` the whole list newest first, waiting Runs included; `run` and `queue` messages carry summaries** (ticket 01). `progress` messages are unchanged. `Runs.onChange` hands listeners a `RunSummary`.
- **Every Run stays in memory forever, in send order, so entries never move** (ticket 01). `MAX_RECENT_RUNS`, `recent` and `forgetOldRuns` are gone; `RunStore.all()` replaces `recentlyFinished`/`unfinished`. `resume()` always reads the history.
- **Run views and summaries carry `finished`, computed on read from `isFinished` in `run-store.ts` and never saved** (second review). Browser code must use `run.finished`, never its own list of states.
- **Inside `Runs`, set a Run's `commit` only through `landedAs(run, commit)` and add Runs loaded at startup through `remember(run)`** (second review); otherwise `get(commit)` misses them in the `byCommit` lookup.
- **Landed changes with no Run record appear as Landed entries whose id is their `Run` trailer or else their commit hash** (ticket 01), so `/runs/<id>` must accept both. Known limitation: they're all placed as older than every saved Run, whatever their dates.
- **Console list markup** (ticket 01): `<ol data-testid="prompts">`; each `li` has `data-run`, `data-state`, `data-original`, and `.state`, `.nickname`, `.prompt`, `.model`, `time`, `.outcome`. Prompts over 80 characters are cut with "…" (full text in `title`). Entries are replaced in place on `run` messages; an open confirmation survives updates.
- **`/api/history` is removed (404)** (second review). `CanvasRepository.history()` is still used internally by `resume()`. Tests list Runs with `platform.listRuns()`; `landing.test.ts` checks the Kind trailer with `git log` so a Prompt still can't forge trailers.
- **Test pitfalls** (ticket 01): in Playwright, `getByRole("button", { name: "Replay" })` also matches "Yes, replay", so use `exact: true`. A test committing straight into the Canvas repo must pass `-c user.name=… -c user.email=…`, since the platform's git identity comes from environment variables the test's `git` doesn't get.

## Run page

- **The Run page is `src/run-page.html`, served at `GET /runs/<id>`** (Prompts list ticket 02): 200 for a known id, 404 otherwise, same page showing "No such Run". It fetches the Run from `/api/runs/<id>`, follows `/api/live`, and refetches the whole Run on every `snapshot` (open and reconnect).
- **`Runs.get(id)` also accepts the commit of a Landed Run** (ticket 02), so both Run ids and commit hashes work, and a Replay's or Rollback's original links to `/runs/<original.commit>`.
- **The Run page refuses cross-origin requests (403) except top-level navigation (`sec-fetch-mode: navigate`, `sec-fetch-dest: document`), and forbids framing (`frame-ancestors 'none'`, `X-Frame-Options: DENY`)** (ticket 02). Canvas code can't fetch or embed it, but shared links open from anywhere. Its data still comes only from `/api/*`. The Console's `/` page has no frame protection yet and could take the same headers.
- **Code shared by Console pages lives in `src/console-shared.js`, served as `/console-shared.js`** (ticket 02; second review): `MODELS`, `modelName`, `runUrl`, `tokenCount`, `usageLine`, `usageSpan`, `detailsOf` (model · time · usage · outcome), `changeLabel` (↻/↩ mark, name and verb), `setStatus`, `fillModels`, `span`, `button`, `connectLive`, `actionsFor(run, {defaultModel, onQueued})` (Replay/Roll back with confirmations) and `queueChange(url, body, what, started)` (resolves to `{ok, what, run, started}` or `{ok: false, what, error}`). New Console pages import these rather than copying; any page that queues a change uses `queueChange`. Each page wraps `setStatus` as `status(message, isError)` on its own `#status`.
- **A Prompts list entry opens its Run page on a click anywhere except a `button`, `select`, `a` or `.confirm`; the shortened Prompt is also an `<a class="open">` link** (ticket 02).
- **The Run page's log and changed-files sections are separate objects, `logSection` (`#log .body`) and `filesSection` (`#files .body`), each with `render(run)` and `live(message)`** (ticket 02). `live` receives every live message for this Run.
- **After queueing a Replay or Rollback from the Run page, the status line links to the new Run's page** (ticket 02).
- **In-progress file names are `RunView.editing?: string[]`, in first-edit order, saved to the Run store as each appears** (Prompts list ticket 04), so they survive reloads and restarts; a resumed Run keeps its earlier names. `editing` stays out of `RunSummary`.
- **Live message `{type:"files", runId, files}` carries every name so far and is sent only when a new name appears** (ticket 04).
- **`GET /api/runs/:id` returns `files: ChangedFile[]` = `{path, added?, removed?, diff?}`** (ticket 04): names only while in progress (and for non-Landed Runs until ticket 05); for Landed Runs, one entry per file from `repo.diff(commit)` with counts and its part of the diff. `changedFilesOf(run, repo)` and `changedFiles(diff)` live in `src/changed-files.ts`; `changedFiles` splits any unified diff, so saved diffs can reuse it.
- **`CanvasRepository.diff()` passes `--no-renames`**, so a rename shows as delete plus add (ticket 04). Per-file path parsing depends on it; Rollback instructions use the same diff.
- **Run page files markup** (ticket 04): `.file` with `.path`, `.additions` (`+N`) and `.removals` (`−N`, a real minus sign); Landed files are `<details>` expanding to `pre.diff` with `.line.{added|removed|hunk|meta|context}`. `changedFilesList(files, {finished})` draws them; an empty list says "No changes" when finished, "No files edited yet" while in progress. When a `run` message says the Run finished, the page refetches it.
- **"View the Canvas at this version" is built from the Console's host plus the Canvas port from `GET /api/canvas` (`{port}`, cross-origin refused)** (ticket 04). The port is the `canvasPublicPort` option (env `CANVAS_PUBLIC_PORT`, set in `docker-compose.yml` to `${CANVAS_PORT:-3001}`), else the listening port. `createConsoleServer` needs `canvasPort: () => number`. The link assumes the Canvas is on the same host as the Console and appears only on Landed Runs.
- **A rejected Run's attempted change is `RunView.attempted?: string`, a unified diff saved with the Run and kept out of `RunSummary`; it's removed when a Run Lands** (Prompts list ticket 05). It's captured in `Runs.inWorktree`'s `finally` block before the worktree is removed, after every attempt, each replacing the last, so only the final attempt remains. A failed read is logged and saved as empty. `changedFilesOf` passes `run.attempted ?? ""` to `changedFiles`, so Runs rejected before this change show "No changes".
- **`CanvasRepository.worktreeChange(worktree)` stages everything (`git add --all`) and diffs against `merge-base HEAD main` with `--no-renames`** (ticket 05). Because it stages, only call it on a worktree about to be removed.
- **Known limitation: if a failed conflict fix is the last attempt, the saved attempted change can contain conflict markers** (ticket 05). Runs stopped by `close()` save nothing until they finish.
- **Known flake: the Run page's Replay test once timed out when only `run-page.test.ts` ran** (ticket 05); it passed on reruns.
- **Playwright: use `exact: true` for "Replay" and "Roll back"** (ticket 02); the Run page also has a "Replay of Bob's …" link.

## Run log

- **The Agent interface has a `message` event, `{type: "message", text}`** (Prompts list ticket 03). `ClaudeAgent` emits it only for non-blank `text` blocks of assistant messages, never thinking, tool calls, tool results or the final result text. `FakeAgent` scripts call `run.message(text)`; Runs ignore blank messages.
- **`RunView.log: LogEntry[]`, with `LogEntry = {time, source: "claude" | "platform", text}`** (ticket 03). It's left out of `RunSummary` and served only by `GET /api/runs/:id` (including the 202 response when a Prompt is queued). Every entry is added through `Runs.log()`, which also sends `{type: "log", runId, entry}` on the WebSocket.
- **The log lives in its own `log` table in `runs.sqlite` (`seq, run_id, entry` JSON, indexed by run and order), one row per entry via `RunStore.appendLog`** (ticket 03), so long logs never slow down saving a Run. `save()` strips `log`; `all()` attaches each Run's log (`[]` for older Runs). No size limit, as decided.
- **Platform log lines** (ticket 03): "Queued", "Started", "Rebasing onto the latest Canvas", "Checking that the Canvas renders", "Fixing a conflict (attempt n of 2)" / "Fixing a render failure (attempt n of 2)", "Starting over from the latest Canvas", "Platform restarted, starting over" (`RESTARTED_LOG_TEXT`, added by `resume()` only to Runs that were in progress), "Landed" (also added by `resume()` when it finds a Run already on `main`), and "Rejected: <reason>". A Run aborted by `close()` gets no line; a resumed Run logs "Started" again.
- **`Lander.land(worktree, change, onStep?)` reports `"rebasing"` and `"render-check"` steps (`LandStep`)** (ticket 03); `Runs.land()` logs them. A Run that changed nothing logs no Landing steps.
- **The Run page holds live messages that arrive while it's fetching the Run, then handles them in order; the log section skips entries it already shows (same time, source and text)** (ticket 03). This also fixed a ticket 02 bug where such messages were dropped and the page got stuck. Log markup: `ol.entries > li[data-source]` with `time[datetime]`, `.source`, `.text`. Selectors for the Run's own time must be scoped (`.details time`).
- **The real-Claude smoke test also checks that Claude's messages reach the log** (ticket 03); it hasn't been run since this change.

- **The log also shows Claude's thinking summaries and its tool calls (name and target, never output), with filter chips Platform · Claude · Thinking · Tools** (user, 2026-10-31; log ticket 01). This supersedes "no tool-call output". Raw thinking is never returned by the API; `ClaudeAgent` passes `thinking: {type: "adaptive", display: "summarized"}` and emits a `thinking` event per non-blank `thinking` block, skipping `redacted_thinking`.
- **Agent events `{type: "thinking", text}` and `{type: "tool", text}`; `LogEntry.source` is `"claude" | "platform" | "thinking" | "tool"`** (log ticket 01). `FakeAgent` scripts call `run.thinking(text)` / `run.tool(text)`; blank text is skipped.
- **A tool entry is held until its `tool_result` arrives (keyed by `tool_use_id`), so a refusal shows in the same entry; tool entries therefore appear after the tool finishes** (log ticket 01). Calls still pending at the `result` message are reported then; a Run stopped or crashed before that loses them.
- **Tool text** (log ticket 01): Read/Write/Edit `"<Tool> <path>"`; Glob `"Glob <pattern>[ in <dir>/]"`; Grep `"Grep '<pattern>'[ in <dir>/]"`; paths relative to the worktree (outside ones as given); ` in …` omitted for the worktree itself; a trailing `/` only for existing folders (one `stat`); other tools just their name. Refusals read "Refused: <call> (<reason>)" with reasons "not available", "not an absolute path", "outside the Canvas", "inside the Canvas's history"; `confineTo(worktree, onRefused?)` reports them. Messages sent back to Claude are unchanged.
- **Confirmed and fixed: in permissionMode `"default"`, Claude Code allows Read/Grep inside its working folder, `.git` included, without calling `canUseTool`** (log review). A programmatic `PreToolUse` hook now enforces confinement for every tool call; `canUseTool` stays as a second check. `confineTo` returns `{ canUseTool, hooks }`, both using one set of rules (a `REFUSALS` table keyed by refusal kind: message to Claude plus log reason) and the same "Refused: …" log text. An allowing hook returns `{}` (not `"allow"`) so Claude Code's own checks and `canUseTool` still run. `settingSources` stays `[]`.
- **`test/claude-agent-sdk.test.ts` runs the real SDK and Claude Code binary from `node_modules` against a local fake Anthropic API (`test/support/fake-anthropic-api.ts`)** via `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and a temporary `CLAUDE_CONFIG_DIR`, so it needs no network or key and runs in the normal suite (log review). It proved the `.git` gap (Read and Grep) and that the hook closes it. The fake picks out main-conversation requests by whether they carry `tools`; a later SDK may change that. Glob and Write/Edit go through the same rules but aren't exercised on the real SDK.
- **One `LOG_SOURCES` table on the Run page (entry label and chip label per source) and one `LOG_SOURCES` mapping plus `isLogged` in `runs.ts` (event type → log source, blank-text check in one place)** (log review). `claude-agent.ts` parses an assistant message once with `blocksOf()`; pending tool calls are handled by `ToolCalls.resultsArrived(content)` and `flush()`.
- **Run page log filters** (log ticket 01): `#log .filters` buttons with `aria-pressed` and `data-source`; hidden sources saved in `localStorage["runLogHidden"]` (JSON array) and applied as `#log[data-hide~="<source>"]`, so CSS hides live entries too. Entry labels: Platform, Claude, Thinking, Tool. The chips' checkmark uses `content: "✓ " / ""` so it stays out of the accessible name.
- **Thinking entries are `--color-text-muted` italic** (`--color-text-disabled` fails AA); longer than one line or 100 characters they become `details.text > summary > .first` plus `.more`, ellipsised when closed; the summary is at least 44px; `.text`'s `textContent` is the full text (log ticket 01).
- **The real-Claude smoke test also checks for a tool entry**; not run since (log ticket 01).

## Resetting the game

- **`scripts/reset-game.sh` resets the game by deleting the whole `data` volume** (2026-11-01, asked for after a manual reset). It runs `docker compose down --volumes`, then `up --detach --build`, and waits for the Console. The platform recreates the Canvas repo from `starter-canvas/` on start. ## Security

- **Every Console API endpoint refuses calls from other origins using `isCrossOrigin()`** (ticket 01). Reuse it on every new endpoint, including the Canvas platform services in ticket 11.
- **Cookies aren't separated by port, so Canvas code can read and overwrite the Console's nickname cookie** (ticket 01). Accepted: nicknames are unauthenticated by design (spec, Out of Scope), and this only matters on the local network. Never put anything secret or privileged in a cookie.
